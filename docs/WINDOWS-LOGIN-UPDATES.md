# Windowsログイン修正と起動時更新

## ログイン失敗の原因

公開認証ページの`Referrer-Policy: no-referrer`により、HTTPSからHTTPのループバックへform POSTする際のOriginがChrome/Edgeでは`null`になった。Windowsの受信口は正確な公開Originを要求するため拒否した。開発者ツールの`com.chrome.devtools.json`に関するCSP警告はこのログイン拒否の原因ではない。

認証完了後、ループバックへのPOSTの直前だけreferrer metaを`origin`へ設定する。参照元のパスやクエリ、認証情報は送らず、公開オリジンだけを送る。Windows側では`null`・他のOrigin・不正なnonce・異なるHost・重複パラメーターを引き続き拒否する。拒否ページは白紙に近い英語表示から、日本語の再試行案内へ変更した。

`scripts/verify-desktop-auth-browser.mjs`は実Chrome/Edge、新しいプロファイル、ダミーFirebase認証、専用のHTTP受信口を使って、実際のHTTPS→ループバックPOSTのOriginとnonce・本文・URL非漏洩を検証する。Google実アカウントや実トークンは使用しない。旧版のWindowsアプリも公開認証ページの修正によってログイン失敗を回避できる。

## 起動時の更新

画面の生成時と既存ウィンドウの再表示時に非同期で更新を確認する。定期ポーリングはせず、通信断でログインや編集を止めない。新しい版があれば小さな案内と「更新して再起動」「あとで」を表示する。設定からの再確認・適用も可能。

正規GitHub Releaseのインストーラーに限定し、Tauri公式updaterで公開鍵署名と署名済みバージョンを検証する。HTTPS・証明書検証を無効にせず、古い版へのダウングレードも許可しない。秘密鍵は配信PC内に置き、CIへ渡さない。配信方法は`DEPLOY.md`を参照。

ダウンロード中の編集は許可する。ダウンロード・署名検証完了後にメモと未送信キューの保存を待ち、保存成功後だけ編集を止めてインストーラーを実行する。転送中は既存の終了確認を行う。失敗時は編集可能な状態へ戻し、再試行できる。二重クリック・複数の更新処理はUIとネイティブ両方で拒否する。未適用の取得済みデータは画面を閉じた際に破棄する。

既存の1.3.89以前にはこの更新機能が入っていないため、新版インストーラーによる初回更新が必要。以降はアプリ内から適用する。単体EXE配布からの更新もインストーラーを使うため、更新後はインストール版として利用する。

## 検証

不要なupdaterのZIP互換機能は無効にして、今回使うNSIS EXEだけを扱う。ZIP 4.6.1の既知の問題3件を含む依存を取り除き、Cargo Auditで既知脆弱性0件を確認した。別OS向けの保守終了等の警告5件はWindows依存経路にないことも再確認した。

TauriはNSISへ入れるEXEのバンドル識別子を`UNK`から`NSS`へ一時的に変更し、ビルド先の元EXEを戻す。このため導入試験では正規の識別子置換だけを期待値に適用し、それ以外の全バイトをSHA-256で照合する。元EXEとの単純なハッシュ一致を要求する誤った試験は修正した。

- Node: 更新前の保存順序、通信・署名失敗、保存失敗、二重実行、オフライン、表示文字列のXSS対策。
- 実Chrome/Edge: no-referrer配信下で、認証のOriginを保ったループバックPOST。
- Rust: nonce・Origin・Hostの検証、分割TCP送信の受信、JS向けのフィールド名、更新URL制限、排他制御、実署名と改変拒否・署名内バージョン。
- GitHub Windows: インストーラーの導入・再導入、インストール済みEXEのハッシュ、クリップボード通知、メモ復元を伴う20回開閉、アンインストール。

OSのインストール試験とクリップボード書込みは使い捨てGitHubランナーだけで行う。実Googleアカウントによる最終ログイン確認と、将来の異なる公開バージョン間の実機更新確認は別途必要。
