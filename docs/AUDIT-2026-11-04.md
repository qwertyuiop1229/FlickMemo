# v1.3.111以降の再点検と採色の追従改善

## 再現して修正した問題

- 保存応答の前に入力を続けると、保存済みの直前の本文がベースに反映されず、自分自身の変更を競合と誤判定し得た。確定した項目だけベースを進め、未送信の本文・タイトル等を同期待ちとして残す。同じメモへの書込みは順に処理し、Firebaseが確定応答より先に返す変更イベントは確定処理後に照合する。待機中の処理は項目名だけを保持し、大きな本文を複製しない。
- 以前のアカウントでのフォルダ書込みが進行中に別アカウントへ切り替え、同じアカウントへ戻ると、古い処理のロックで新しいセッションの再送が止まる場合があった。処理をアカウントとセッション世代の両方で区別する。古い世代の失敗通知も新しいセッションへ表示しない。
- フォルダの内容や件数が変わらない本文保存でも、フォルダのDOM全体を毎回作り直していた。表示内容を比較し、同じ場合は再利用する。キーボードのフォーカスも保持する。
- 永久削除中・削除済みのメモを、進行中の保存が「競合の控え」として作り直さないよう確認を加えた。
- 受信の保存先選択ダイアログの結果が、アカウント切替・保存先解除の後に遅れて戻る場合を拒否する。画面側とWindowsネイティブ側の両方で世代を照合し、古いダイアログが保存権限を復活させない。解除完了前に新しい選択を始めないようにし、解除失敗も通知する。

## 採色の処理

既存のUI・色形式・ショートカット・拡大表示・コピー操作を維持。マウス入力専用スレッドでは画面取得や描画をせず、約15ms以上の間隔・最大1件の待機通知で追従処理へ伝える。大量のマウス入力を蓄積しない。通常の追従は入力イベントで行い、停止中の動画などの採色と最後の位置の確認は33msタイマーで行う。以前の15msタイマーより定期起床を減らす。

カーソルが止まっている間はモニター・DPI・ウィンドウ位置の再計算を省く。モニター構成/DPI/作業領域の変更では明示的に再配置し、再入可能なWindowsメッセージ内で同じ状態を二重に借用しない。採色は引き続き7×7ピクセルのみで、描画バッファ・GDIオブジェクトは再利用し、停止時に解放する。全画面画像や常駐GPUキャプチャは追加しない。

初回の比較試験では入力側と追従側の二重の時間制限がフレームを落とし、旧版49.9fpsに対し試作38.1fpsとなったため、公開を止めた。追従側で再び間引かず、入力スレッドで通知数だけを制限する方式に修正。位置だけの更新ではWindowsにサイズ・前後関係の変更を要求せず、失敗した移動を追従回数へ加算しない。最終測定は720ステップへ延長して短いCPU計測の揺らぎを減らす。

続く比較でも旧版52.1fpsに対して試作41.4fpsだったため公開しなかった。マウスフックが通知した座標を64ビットの原子的なスナップショットとして保持し、追従側でGetCursorPosを読み直さず最新イベント座標を使う。フックの戻りとOS座標更新のタイミング差を避け、通知待ちの間に届く新しい座標も置き換える。負座標を含む仮想デスクトップ座標の往復を純粋な単体試験に追加した。

ウィンドウ処理が再入した場合には、状態の借用とは独立して移動通知を受領する。借用中の通知を繰り返しキューへ戻す処理は使わず、次の入力/定期確認で最新位置を反映する。通知の再送ループによるCPUの浪費を避ける。

## 検証方針と範囲

Nodeの回帰試験で、保存中の連続入力・早いFirebase確定イベント・アカウント切替後の待機書込み破棄・フォルダ再送・フォーカス保持を検証する。既存の暗号化転送・受信上限交渉・32KiB読出し・80MiB仮想ストリーム・保存失敗時の部分ファイル破棄・不正なノート/名前・更新署名の回帰試験も実行する。

Windows CIの使い捨て環境でv1.3.111と修正版に同じ合成マウス入力を与え、追従回数・CPU・PrivateMemoryを比較する。今回の入力は実際のマウス移動フックを通る方式で、以前のPowerShellのSetCursorPosだけの計測とは入力頻度が異なる。そのため以前の約34fpsと今回の数字を直接の倍率として扱わない。停止中の再配置なし・採色の継続・低CPU、10回の起動/中止でのGDI/USERリソース数も確認する。インストール・再インストール・v1.3.111からの更新・20回の表示/休止・設定・自動起動登録/解除・アンインストールを確認する。

個人端末の実クリップボード・画面取得・入力フック・起動設定・実インストーラーは操作しない。ブラウザは新規のヘッドレスプロファイルで確認する。実iPhoneの大容量ファイル、実Google認証、全GPU/全DPI/複数モニターの組合せ、長期間常駐、OSやWebKitの一時ファイル回収までは保証しない。

2026-11-04のnpm auditでは本番依存と開発依存を含む全依存の両方で、既知の脆弱性は0件だった。これはコードの安全性や将来の脆弱性不在を保証するものではない。

Cargo.lockのレジストリ依存526バージョンをOSVに照合したところ、glib 0.18.5のRUSTSEC-2024-0429（GHSA別名あり）と、proc-macro-error・zbus_names・zvariant・zvariant_deriveの保守終了通知に該当した。`cargo tree --locked --offline --target x86_64-pc-windows-msvc --edges normal,build` でWindows版の実際のビルド/通常依存関係を確認し、これら5パッケージが含まれないことを確認した。ロックファイル全体を「検出ゼロ」とは報告しない。今回のWindows版に含まれないGTK/DBus等の依存は、他OS版を作る際に再点検が必要となる。

照合方法: https://google.github.io/osv.dev/post-v1-querybatch/ 。通知の一次情報: https://rustsec.org/advisories/RUSTSEC-2024-0429.html 、https://rustsec.org/advisories/RUSTSEC-2024-0370.html 。入力座標の仕様: https://learn.microsoft.com/en-us/windows/win32/api/winuser/ns-winuser-msllhookstruct 。

実測と公開結果は最終検証後に追記する。

採色の速度・CPU・コピー・10回の中止を通過した後、更新試験が7分で時間切れとなった。そのため、処理ごとの期限とネイティブの表示状態、実行プロセス/DevTools targetの記録を追加した。前のプロセスのtargetを再利用せず、終了も待ってから次のアプリへ接続する。画面が休止している間はJavaScriptで状態を問い合わせない。既存v1.3.114の同じ成果物を再ビルドせず検証した診断実行 https://github.com/qwertyuiop1229/FlickMemo/actions/runs/41812595186 では、1.3.111からの更新、メモ保持、表示/休止/復帰、自動起動登録/解除、アンインストールをすべて通過した。診断用workflowは読み取り権限のみで、配布ファイルを公開しない。

Edgeの80MiB試験では、60秒・毎描画フレームでの完了監視が時間切れとなった。一方、転送量を追跡した確認と、250ms間隔の監視では約50秒で13項目すべてが成功した。試験の監視負荷を減らし、大容量の全体制限時間を180秒へ変更した。実際の転送処理の「30秒進展なし」のタイムアウトは変更しない。
